# TUI rebuild: list component, search, colours, input and editing

**Date:** 2026-11-12
**Status:** In progress (steps 0 to 2 done; step 3 next)
**Supersedes:** the abandoned `origin/tasklist-2` branch (a 2025 spike
with the same aims, unmergeable after the May refactor). Started fresh
on `main`; only its ideas carry over.

## Motivation

The TUI draws its task list by hand: no paging, no search, every task
in one colour, a bare text box for new tasks, and no way to edit one
task short of opening the whole file in `$EDITOR`. Bubble Tea's `list`
component brings paging and filtering; the rest is ours to build.

## Decisions captured

From the design dialogue (2026-11-12):

1. **Four steps, each merged on its own** with the suite green:
   0. groundwork with no behaviour change;
   1. the list component and search;
   2. colours;
   3. input and editing.

2. **Search matches text plus the CLI's filter words.** In the search
   box, a word that is a `htt todo show --filter` expression
   (`overdue`, `due-soon`, `no-due`, `has-tag:NAME`, `priority:X`) is
   applied as that filter; every other word is matched fuzzily against
   the task line. All parts must match. The CLI and TUI therefore
   share one filter implementation, which moves out of `internal/cli`
   (step 0).

3. **Actions act on the selected task, never on its position in the
   view.** With a search applied, the third row on screen isn't the
   third task in the file. Each list item carries its task's index in
   the context, and every action (complete, delete, priority, edit)
   uses that. This is the step's main correctness risk and gets the
   most tests.

4. **htt's keys win over the list's defaults.** The list binds
   `h`/`l`/`f`/`d` to paging and `q`/`?` to quit and help, which clash
   with htt's context switching, edit-file, delete, quit and help.
   Paging moves to PgUp/PgDn (Home/End and `g`/`G` for the ends), and
   htt keeps quit and help. While the search box has focus, keys go to
   it. Esc clears an applied search; with none, Esc quits as today.

5. **Colours are theme roles.** Step 2 colours each task line by
   token: priority (A, B, C), `+project`, `@context`, `#tag`, and
   "meta" (dates and `key:value` pairs). These become new roles in
   every built-in theme and in `tui.colors`, and the contrast tests
   cover them. Tasks in the done tab render in `muted`. (Revised while
   building step 2: see Progress.)

6. **Input and editing (step 3), all four asked for:**
   - `e` opens the selected task in the input box, pre-filled; Enter
     saves it in place, Esc cancels.
   - A live preview line shows the task as it will be saved, coloured
     like the list, with a warning when something won't parse as
     meant.
   - Tab completes `+project`, `@context` and `#tag` from the tags
     already used across all contexts.
   - Natural due dates: `due:friday` or `due:"in two weeks"` resolve to
     `due:YYYY-MM-DD` on save, using the same phrase parser as
     `htt todo add --due` (shared in step 0). A phrase that doesn't
     resolve blocks the save and says why.

## Progress

- **Step 0** (2026-11-12): filters in `domain`, date phrases in
  `internal/dates`; CLI unchanged.
- **Step 1** (2026-11-12): the list component and search, as planned.
  Settled while building it:
  - the cursor follows a task whose priority change re-sorts it (a
    wishlist item, free once items carry their index);
  - a search stays applied across actions and tab switches;
  - Enter on a search with no matches clears it (the list component's
    own behaviour, kept);
  - an action with nothing selected (empty list or search) is a warning
    that keeps the TUI open, not an error that quits;
  - search results arrive as a separate message, so every message that
    isn't one of htt's keys goes to the list (the 2025 branch dropped
    them, and its search never narrowed).
- **Step 2** (2026-11-12): task lines coloured by token. Settled while
  building it:
  - the tokenizer is `domain.Tokens`, not a second grammar in
    `internal/tui`: it walks the parser's own tree, so a colour always
    matches what htt understood, and a property test holds it to
    `NewTask`;
  - writing it turned up parser bugs, fixed first as their own
    changes: words dropped or split, so a priority change or
    completion lost text from the file, and panics on a lone `+`, `@`
    or `#` (`fix/parser-words`); a hang on a line with over 100 tags
    (`fix/query-hang`). `rebuild` moving annotations is recorded in
    `TODO.md`;
  - roles: `priority_a`, `priority_b`, `priority_c`, `plus_tag`,
    `at_tag`, `hash_tag`, `annotation`, `date`. Tags are named by
    sigil because "context" already means a task list in htt, and
    "meta" became `annotation` and `date`;
  - the done tab gets the same colours, not `muted`: `muted` is 2.4:1
    on the background in the default and Nord themes, too dim to read;
  - the selected row keeps `foreground` on `selection`: token colours
    can't all reach 3:1 on mid-tone selection colours;
  - search matches are underlined, keeping each word's colour, so no
    role is needed. Match positions are byte offsets (the list's own
    delegate treats them as runes, wrong for non-ASCII);
  - rows are cut to the list's width with "…", and whitespace is drawn
    as spaces (a tab or a CRLF file's `\r` broke the row);
  - each built-in theme maps its canonical colours onto the roles,
    except solarized-light's yellow, green and cyan, darkened to reach
    3:1.

## Steps

### Step 0: shared filters and due phrases

- `domain`: `Filter`, `ParseFilter(expr, now)`, `Task.Due()`,
  `Task.HasTag(name)`, and `ParseLocalDate`. `htt todo show --filter`
  uses them; its errors and output are unchanged.
- `internal/dates`: `ParsePhrase(input, now)`, moved from
  `internal/cli/due.go`; `--due` uses it.
- Tests move with the code; the CLI tests keep passing untouched.

### Step 1: the list and search

- The task list becomes a `list.Model` with a custom delegate that
  draws rows as today (cursor, index, text, selection colour).
- Search as in decision 2, through the list's `Filter` function.
- Key handling as in decision 4.
- Tests: actions under an applied search hit the selected task;
  paging; search with filter words, text and both; Esc behaviour.

### Step 2: colours

- A task-line tokenizer and renderer; the new theme roles; search
  matches highlighted. (Done: see Progress.)

### Step 3: input and editing

- As in decision 6. Tests per feature; a real-terminal check.

## Out of scope

- Sorting in the TUI.
- Multi-line task input.
- Changes to the CLI beyond step 0's move (e.g. due phrases inside
  `htt todo add` text).
