# Subtasks: building the agreed design

**Date:** 2026-11-23
**Status:** In progress

## Motivation

Build subtasks exactly as [docs/design/subtasks.md](../../design/subtasks.md)
describes them (Brice's design of 2026-11-23, with the TUI's one-level
nest and unnest and priority order among subtasks added the same day).
The design says what subtasks are and how they behave; this plan says
how they're built and tested. Where building shows the design needs to
change, that part stops and is reported, not guessed.

## Choices

### The tree

- **It lives in the domain**, in `internal/domain/tree.go`:
  `NewTree(tasks, doneIDs)` builds it from a context's tasks, purely;
  `Context.Tree()` builds it for a loaded context, reading the done
  file only when some `p:` names no task in the context's own file
  (most loads never read it).
- **A task's id is its first `id:`**, as topydo reads it
  (`tag_value('id')`); links match by exact text, as topydo's do, so
  `p:01` doesn't name `id:1`. A task's parent is named by its first
  `p:` (the design's "each task under its first parent").
- **The context's done file.** htt has one `done.txt` for every
  context; a context's done tasks are those whose `context:`
  annotation names it, as `Context.Complete` writes them. A `p:`
  naming the id of one of those is a done parent.
- **The done file and the archive aren't trees.** They collect tasks
  from every context, so their ids aren't a namespace: htt shows them
  flat, never reorders them and warns about no links in them. Adding,
  nesting and unnesting there are refused; deleting or moving from
  them takes one task.
- **Broken links** are `LinkProblem`s on the tree (a task index and a
  message), each shown at the top level: a `p:` naming no task (nor a
  done one); every task of a loop; a task whose parent's id is on
  several tasks (the warning is on each task holding that id); several
  `p:` on one task, which stays under its first parent (the design's
  format section says so explicitly; its broken-links list puts it
  among the problems that warn).

### Order

- **`Arrange`** puts a context's tasks in tree order: a depth-first
  walk from the top-level tasks, which keep their order; each parent's
  subtasks sorted by priority, `(A)` to `(Z)` then none, stably. It
  only permutes pointers: no line is read back, rebuilt or dropped.
- **On write.** Every persistent `Context` method saves through one
  helper, `Context.save`, which arranges the tasks (and renumbers
  `Line`) before `Repository.Save`. Nothing else writes a context.
- **On read.** `FileRepository.Context` and `MemoryRepository.Context`
  arrange what they read, so a task's number is its place in tree
  order even in a file another tool left out of order, and the tree
  always reads top to bottom in number order. `Line` is the index
  after arranging; `FileLine` stays the line in the file, for
  warnings. A file htt wrote is already in order, so its numbers don't
  change.
- **Priority changes** still sort the context by priority before the
  write, as in 1.0 (the file is sorted after each priority change), so
  top-level tasks sort as they did; `Context.Sort` becomes stable so
  equal priorities keep their order, which the design asks of
  subtasks. The TUI's priority keys stop sorting the reloaded context
  again in memory, which would break the tree's order.

### Ids and arranging

- **Ids:** the smallest whole number whose text no `id:` or `p:` in
  the file uses (every occurrence counts), topydo's `find_next_id`.
- **Adding under N** appends the task with `p:` naming N (N gets an
  `id:` first if it has none); arranging puts it after N's last
  descendant, or at its priority place among N's subtasks.
- **Nesting N under M** moves N's subtree to just after M's subtree,
  then sets N's `p:`, so it lands last among M's subtasks of its
  priority. A task with several `p:` keeps one. A loop is refused, as
  is a parent whose id is on several tasks (a link to it couldn't
  resolve).
- **Unnesting N** (CLI) removes its `p:` tags and moves its subtree to
  just after its top-level ancestor's subtree. A task with no `p:` is
  already top-level: an error.
- **The TUI's one-level moves:** Tab nests the selected task under its
  previous sibling in the tree (its subtree follows it already, so it
  only gets a `p:`); Shift-Tab makes it a sibling of its parent,
  moving its subtree to just after the old parent's subtree, under the
  grandparent or at the top level. `ErrNothingAbove` and
  `ErrTopLevel` say why nothing changed.
- **Moving between contexts** moves the subtree. Into a context file,
  the moved task loses its `p:` (a parent is always in the same file)
  and any of the subtree's ids that clash with an `id:` or `p:` value
  in the target is renumbered to the target's smallest free id, its
  `p:` links rewritten with it. Into the done file or the archive the
  lines go unchanged.
- **Deleting** archives the subtree, in tree order, each line
  annotated as before.
- **Completing** takes a `Subtasks` choice: `SubtasksAsk` (the zero
  value: refuse, with `ErrOpenSubtasks`, when there are open tasks
  below), `SubtasksLeave` (`x`) or `SubtasksComplete` (`A`, every open
  task below at any depth, in tree order). The prompt's count is the
  open tasks below at any depth, which is what `A` completes.

### The completion prompt

- **A terminal** is stdin and stdout both terminals (`isatty`, as the
  REPL checks for the TUI). Without one, and without `--leave-subtasks`
  or `--with-subtasks`, `todo do` fails naming both flags (exit 1).
  Both flags together are an error.
- **Asking:** the four lines of the design on stdout, then one line
  read from stdin a byte at a time (so nothing past it is taken). The
  answer is the line without its `\n` or `\r\n`: exactly `x` or `A`;
  anything else, or end of input, cancels (`Cancelled: nothing
  changed.`, exit 0).
- **In the REPL** the question runs through `runOnTerminal`, the REPL's
  `replTerminal.handOver`, as the TUI does: readline is closed while
  the answer is read, then reopened.

### Showing

- **`htt todo show`** (and `htt todo`, `todo status`, `htt status` and
  the REPL's view) print the tree: two spaces a level after the number;
  a task whose parent is in the done file ends with `(parent done)`.
  `--flat`, `--sort`, `--filter` and `search` print the plain list.
- **Warnings** for broken links go through the date warnings' path
  (`warning: <file>:<line>: <message>` on stderr, once a run), and a
  typed task's command (add, add-to, replace, edit) warns about links
  it broke once it's saved.
- **The TUI** draws the tree with the same indentation, and
  `(N folded)` or `(parent done)` in the muted colour at the end of a
  row; `id:` and `p:` words are muted. Folds are per session, keyed
  by context and id; a search ignores them and shows its rows flat.
  Link warnings join date warnings on the status line.
- **TUI keys** (free in today's keymap and the list's): `s` adds a
  subtask under the selected task, `Tab` nests it under the task
  above, `Shift-Tab` unnests it a level, `Space` folds or unfolds it.
  The selection stays on the task moved; nesting under a folded task
  unfolds it. `x` on a task with open subtasks puts the design's
  question on the status line; the next key answers it (`x`, `A`, any
  other cancels).

## Stages

Each a commit that builds and passes its tests:

1. **The tree and ids** (`tree.go`): building, problems, done parents,
   arranging, id allocation. Pure.
2. **File order on write and read:** `Context.save`, the repositories
   arranging on load, stable `Sort`.
3. **Commands:** the domain operations (add under, nest, unnest, the
   one-level moves, subtree delete and move with renumbering, complete
   with a choice) and the CLI's `--under`, `nest`, `unnest`, `delete`
   and `move` listing what they took, link warnings.
4. **The completion prompt and flags,** CLI and REPL.
5. **`show`:** the tree, `--flat`.
6. **The TUI.**
7. **Docs:** GETTING-STARTED, README, command help, the REPL help,
   TODO.md, docs/architecture.md, the design's status line, this plan
   moved to `complete/` with its outcome.

## Testing

Tests first where they can be, seen failing.

- **Domain, table tests:** each kind of broken link and done parent;
  ids (smallest free, counting `p:`, by text); add under, nest (loop
  refused), unnest, the one-level moves and their "nothing to do"
  cases; move with renumbering (links kept, no clash); delete of a
  subtree; complete with each choice; a priority change moving a
  subtask among its siblings.
- **Domain, property tests** over generated files (lines htt
  rewrites: dates, priorities, done marks; broken links, loops,
  duplicate ids, several `p:`, done-file parents, non-numeric ids):
  arranging is a permutation of the input lines with every line
  unchanged, idempotent, keeps subtrees contiguous under their
  parents, keeps top-level order and sorts siblings by priority
  stably; ids unique and smallest free; moves and renumbering keep
  every line and every link.
- **Through the file repository:** a generated file loads, saves and
  loads again as the same lines; a file in order is written back
  byte-identical.
- **topydo:** a multi-level file as topydo writes it (children before
  and after parents, tags at the end) reads as the tree topydo's rule
  gives; after htt's writes, a test reimplementation of topydo's rule
  reads the same tree back.
- **e2e:** every command; `show`'s indentation and `--flat`, sorted
  and filtered views flat; a command after a reordering write acting
  on the task shown; warnings on stderr once a run; the completion
  prompt through a pseudo-terminal (`x`, `A`, other, end of input),
  in the REPL too; the flags without a terminal, and the refusal.
- **TUI:** the tree unfolded by default; fold and unfold; `s`, Tab
  and Shift-Tab, including their "nothing to do" cases and a task
  with a subtree of its own; the prompt; muted tags; priority keys
  keeping the selection on the task.
- **Mutations** on the core rules, each named with the test that
  caught it; a survivor gets a test.
