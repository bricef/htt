# Subtasks: tasks within tasks, in todo.txt

**Date:** 2026-11-23
**Status:** Planned

## Motivation

Brice wants tasks that hold other tasks, to break work down. todo.txt
has no notion of it, and its rules rule out the obvious shapes:
indenting a line breaks the `x ` done marker and doesn't survive a
tool that sorts the file, and a sidecar file of links breaks as soon
as another tool edits a line. What the format does allow is any
`key:value` tag, which tools that don't know it keep as text.

topydo already records dependencies that way: the parent gets `id:N`,
each child `p:N`, N the smallest number no task in the file uses as an
`id:` or `p:` (topydo's `TodoList.add_dependency` and `find_next_id`).
htt adopts the same tags, so a file stays valid todo.txt everywhere,
survives other tools' sorting and editing (the links are by id, not by
position), and reads the same in topydo.

```
(A) Plan the launch +work id:1
Write the announcement p:1 +work
Book the venue p:1 id:2
Call three venues p:2
```

## Decisions

Brice's decisions of 2026-11-23 are 1, 2, 3, 4, 5 and 6; the rest are
the details they need.

1. **Completing a task with open subtasks asks first.** On a terminal:

   ```
   Task 3 has 2 open subtasks.
   [x] Mark it done, and leave the subtasks as they are.
   [A] Mark the subtasks done too.
   Anything else cancels.
   ```

   `x` completes the task alone; `A` completes it and every open task
   below it, at any depth; anything else changes nothing. The TUI asks
   the same, with the same keys. Without a terminal (a script, piped
   input) there's no prompt: the command fails, saying so, unless
   `--leave-subtasks` (as `x`) or `--with-subtasks` (as `A`) is given.
   Completing the last open subtask doesn't complete its parent.
2. **A tree:** a task has at most one parent. A task with several `p:`
   tags (topydo allows it) sits under the first, with a warning.
3. **Subtrees travel together.** `htt todo move N CONTEXT` moves a
   task with everything below it; `htt todo delete N` archives it with
   everything below it, listing what went. Ids are unique within a
   context file, and a parent is always in the same file as its
   children, so each file stands alone for other tools; a subtree
   moved into a file whose ids clash is renumbered there, its links
   kept.
4. **Line numbers stay the way to address tasks** (`htt todo do 3`),
   as the 1.0 promise has them. When htt writes a context file it puts
   every subtree directly below its parent, keeping the order of
   siblings and of top-level tasks, so the tree reads top to bottom in
   line-number order. Adding a subtask inserts it after its parent's
   last descendant, which shifts the numbers below it, as deleting a
   task already does. A file already in that order is written back
   unchanged; no line is ever dropped.
5. **Broken links warn, and lose nothing.** A `p:` naming no task, a
   loop, two tasks with the same `id:`, or several parents: htt warns
   (stderr once per run on the CLI, the status line in the TUI, as for
   dates it can't read) and shows the task at the top level. A `p:`
   naming a task in the context's done file isn't broken: that's a
   parent completed with `x`, and its subtasks show at the top level,
   marked as having a done parent, without a warning.
6. **The tags stay visible.** `id:` and `p:` are shown wherever a task
   is, in full; the TUI draws them in the theme's `muted` colour, so
   the task's text stands out. No new colour role.
7. **Showing the tree:**
   - `htt todo show` indents each subtask under its parent, after the
     line number (two spaces a level).
   - `--flat` gives the plain list, and so do sorted and filtered views,
     where the tags still say what belongs to what.
   - The TUI shows the tree with collapse and expand, and keys to add a
     subtask and to nest or unnest a task. The keys are to be fitted to
     the existing keymap; outliners' Tab and Shift-Tab are the natural
     candidates for nest and unnest.
8. **Commands:**
   - `htt todo add --under N TEXT` (and `add-to`) adds a subtask of
     task N, giving N an `id:` if it has none.
   - `htt todo nest N M` puts task N, with its subtree, under task M.
     A loop is refused.
   - `htt todo unnest N` makes N a top-level task: its `p:` goes, and
     its own subtree stays with it.
   - A parent left with no children keeps its `id:` until
     `htt todo tidy`, or a normal write, removes ids nothing points to.
     Whether ordinary writes do that is the implementer's call; say
     which.
9. **Compatibility:** additive. Existing files are unchanged until a
   subtask is made, and htt 1.0 shows `id:` and `p:` as ordinary tags.
   Under docs/releasing.md this is a minor release (1.1.0).

## Testing

- **Domain (the tree):**
  - Building it from lines: ids, parents, warnings for each kind of
    broken link, done parents.
  - Normalising the file order, with property tests over generated
    files: idempotent; the same lines out as in; every subtree
    contiguous under its parent; siblings' order kept.
  - Id allocation: unique, smallest free, as topydo's.
  - Moving and renumbering a subtree: no clashes, links kept.
  - Deleting a subtree.
- **Completion:** each answer to the prompt, at depth; the flags;
  refusal without a terminal and without a flag. The prompt is driven
  through a pseudo-terminal, as the REPL→TUI test does.
- **Round trips:** a file written by topydo (several levels) reads as
  the same tree; htt's output reads back in topydo's shape.
- **e2e and TUI tests** for each command and key; mutation checks on
  the tree rules.

## Out of scope

- Several parents (a dependency graph), "blocked by" semantics,
  inheriting priority, due dates, projects or contexts from a parent,
  progress counts in reports, subtasks in `htt gui`.
