# Subtasks: building the agreed design

**Date:** 2026-11-23
**Status:** Complete (2026-11-23)

## Outcome

Built on `feat/subtasks`, in the stages planned, each a commit with
its tests: the tree and ids; the file order on write and read; the
operations and the CLI's commands; the completion prompt and its
flags; `show`; the TUI; then two follow-ups (the done file read once
and only where it can matter; moves the mutation checks found
redundant, removed); these docs. The design was followed as written;
where it left a reading open, the choice is below.

Readings of the design:

- **Several `p:` on a task.** The format section says such a task is
  read "under its first parent, and a warning"; the broken-links
  section lists it among the problems whose tasks show at the top
  level. Built as the format section says: under the parent its first
  `p:` names, with a warning. If that `p:` names nothing, the task is
  at the top level, with both warnings.
- **The prompt's count** is the open tasks below the task at any
  depth, which is what `A` completes, so `[A] Mark the subtasks done
  too` does what the count says. ("Subtask" in the terms is a direct
  child; a direct-children count would understate `A`.) With one, the
  line reads "1 open subtask".
- **The context's done file.** htt keeps one `done.txt` for every
  context; a context's done tasks are those whose `context:`
  annotation names it, as completing writes them. A `p:` naming the id
  of one of those is a done parent; the same id completed from another
  context is a broken link.
- **The done file and the archive aren't trees.** They hold tasks from
  every context, whose ids clash, so they're shown flat and never
  reordered or checked for links. Adding under, nesting and unnesting
  there are refused; deleting or moving from them takes one task;
  moving into them leaves the lines as they are.
- **A move drops the moved task's `p:`**: a parent is always in its
  subtasks' file, so in the target it's a top-level task. A clash is
  an id the target already uses as an `id:` or a `p:` (a `p:` naming a
  done parent there holds its number, by the same rule as new ids).
- **Unnest** (CLI) removes every `p:` on the task, so it also clears a
  broken link or a done parent; a task with no `p:` is refused as
  already top-level. It lands after the top-level task it was under,
  the TUI's rule for a subtask of a top-level task.
- **Nesting under a task whose id another task holds** is refused: a
  `p:` naming it couldn't resolve. A loop is detected by following the
  tags, so two tasks already in a loop (both shown at the top level)
  can't be closed into one again.
- **Cancelling the prompt** prints `Cancelled: nothing changed.` and
  exits 0, as an edit left unchanged does. Without a terminal (stdin
  and stdout both one) and without a flag, `do` exits 1, naming both
  flags; both flags together are an error.
- **Priority changes** still sort the whole file by priority before
  the write, as 1.0 does ("the file is sorted by priority after each
  priority change"), so top-level tasks sort as they did; the
  normalisation itself never sorts them. `Context.Sort` became stable
  so ties keep their order, as the design asks of subtasks, and puts
  no priority after `(Z)` too (it ranked them together).

Choices made while building:

- **Numbers follow the tree on read too.** The repositories arrange a
  context as they load it, so a file another tool left out of order
  is numbered in tree order, the order htt will write it in: `show`'s
  numbers always ascend down the tree, and every command takes the
  same numbers. A file htt wrote is already in order, so nothing
  changes for it. `FileLine` stays the file's line, for warnings.
- **Marks.** `(parent done)` after a task whose parent was completed,
  in `show` and the TUI (muted there); `(N folded)` after a folded
  task in the TUI.
- **TUI keys:** `s` adds a subtask, `Tab` nests under the task above,
  `Shift-Tab` unnests a level, `Space` folds and unfolds; none was
  bound, by htt or the list. The question takes the next key; Ctrl-C
  still quits. A search looks through folded tasks, flat, and the list
  folds again after it. Moving a task under a folded one unfolds it,
  so the cursor stays on the task.
- **Warnings.** Broken links warn as dates do, once a run, naming file
  and line, each task's after its dates; a typed task's command warns
  about links its change broke (a parent replaced without its id).
- **Reading the done file.** Only when a link doesn't resolve in the
  context's file, once per loaded context, and only the lines with an
  `id:` and the context's `context:` are parsed (`domain.LineSource`,
  which both of storage's repositories are): a done parent cost 1.7s
  a command with 3000 completed tasks when every line was parsed,
  0.06s now.
- **Placing.** Only `Nest` moves a subtree in the list before
  arranging (to just after its new parent's subtree). A task taken out
  of a subtree (`unnest`, Shift-Tab) or put under the task above (Tab)
  already sits where the design puts it in a list in tree order, and
  arranging keeps it there; the moves first written for them were
  found redundant by the mutation checks and removed.
- `Context.Show` went: the CLI prints the tree (`printContext`).

Tests: as planned. Table tests for every operation, refusal and kind
of broken link; property tests over generated files (preambles htt
rewrites, odd words and spacing, tags anywhere, textual and
leading-zero ids, broken links, loops, duplicates, several `p:`, done
ids) for the tree, ids, arranging (a permutation, every line
unchanged, idempotent, subtrees contiguous, siblings by priority and
stable, top-level order kept), every arranging operation, moves with
renumbering, deletes and completes; through the file repository,
every line kept and a file in order written back byte for byte; e2e
for every command, show and `--flat`, numbers after a reordering
write, warnings once a run, the prompt through a pseudo-terminal (x,
A, other answers, end of input), in the REPL, without a terminal and
with the flags; topydo's rule reimplemented apart from htt's parser,
reading a topydo-shaped file and each of htt's writes as htt does; TUI
tests for each key and the question. Outside the suite, topydo 0.16's
own `TodoList` read a file htt wrote, and htt read one topydo wrote
with `add_dependency`, four levels deep: the same tree both ways.

Mutations: 54, each breaking one rule, run against the domain,
storage, CLI and TUI packages and the e2e and TUI suites. Every one
is caught now but two that changed nothing, whose code is gone; what
wasn't caught at first changed the code or the tests:

- **The tree** (14): the parent named by the last `p:` (`NewTree`,
  its properties, several-parents nest, the stderr warnings); subtasks
  unsorted, ties reversed, the top level sorted, no priority first (the
  tree's table and property tests, both repositories' contract,
  add-under, Tab, Shift-Tab, the priority e2e, topydo's, the TUI); a
  loop left in place, a duplicated id resolved to its first holder (the
  tree's, arranging's and the file's properties); no warning for a
  duplicated id or several `p:` (`NewTree`, the stderr e2e); a done
  parent read as broken, done parents from any context (`Tree`'s done
  parents, the e2e, the TUI); an id read from the last `id:`
  (`ID`); `NextID` ignoring `p:` or starting at 0 (`NextID` and its
  properties, add-under, moves).
- **Order** (5): writes not arranged (unnest a level, add-under e2e,
  the TUI); loads not arranged (the contract, the file property,
  numbers e2e, topydo's); the done file and archive arranged (the
  contract, arranging's property, delete, move into done, refusals);
  the priority sort unstable (the stable-sort test); priority changes
  not sorting the file (1.0's own tests, the subtask priority tests).
- **Operations** (17): nest without the loop check, under a shared id,
  without moving the subtree; unnest keeping `p:`; Tab under the next
  sibling; Shift-Tab always to the top; moves without fitting in,
  keeping the root's `p:`, leaving `p:` links unrenamed, counting only
  the target's `id:`; delete taking one task; `A` completing done tasks
  too; completing without asking; no parent id; several `p:` kept:
  each by its table test and the property tests, most by e2e and the
  TUI too. Two survived: unnest placed after the immediate parent, and
  Shift-Tab without moving the subtree. Both are equivalent: in a list
  in tree order the task is already where the design puts it, so those
  moves (and Tab's) were removed. A clash counting only the target's
  `id:` and nest without its move were each caught by one test, so
  each has a second (a table test of a clash through a `p:`; the
  arranging property checks a nested task is last of its priority).
- **CLI** (10): answers case-insensitive, trimmed, end of input as
  `x`; stdin alone taken for a terminal; no refusal without one;
  show indenting one space; no `(parent done)`; no link warnings;
  `--flat` and the completion flags not reset in the REPL. "stdin
  alone" made the stdout test wait on the terminal until go test's
  timeout: it now gives htt ten seconds. `--flat` not reset failed
  only the reset's unit test: the REPL e2e now counts flat listings.
- **TUI** (8): `id:`/`p:` not muted (the colour test); `a` taken for
  `A`; folds hiding nothing; a search skipping folds; a move leaving
  its new parent folded; `x` not asking; rows not indented (the TUI
  tests). Sorting the reloaded list again after a priority change
  survived: the test's change left the order alone. It now raises a
  subtask above its parent's priority, where the second sort would
  pull it out from under it.

Four mutations didn't compile as first written (nest's move, several
`p:`, link warnings, folds) and were rewritten and caught.

After review (2026-11-23). An independent review found five bugs and
three nits, fixed on the branch, each with tests seen failing first
and mutation-checked:

- **A move to the current context under another spelling** (`move 0
  "my list"` in my_list) wrote the subtree to the file, then saved the
  context without it over the same file. Names are compared as files
  are named, by the domain's `ContextFileName`, which both
  repositories now name files by; the move is refused.
- **The TUI saved its stale list** over what another htt wrote while
  it was open (already so on main), and `s` added under the task at
  the stale index in the reloaded file. Every action that changes
  tasks reloads the file first and finds the task shown by its line;
  a task changed or removed elsewhere is left alone, and the status
  line says so. Tab checks the task above it is the one shown, and
  the answer to `x`'s question the subtasks it counted.
- **A task whose only text is its `p:`** became an empty line on
  `unnest`, Shift-Tab to the top or `move`. Refused (`ErrOnlyLink`).
- **A done parent moved back** from the done file to its own context
  was renumbered (its subtasks' `p:` held its number), breaking their
  links. It keeps its id when the `p:` there can name nothing else,
  and a done subtask moved back keeps its `p:` when its parent is
  there (unless that would make a loop), so "A move drops the moved
  task's `p:`" above holds except for a done task coming home.
- Nits: an empty or non-number `--under` is an error; an update
  notice waits while `x`'s question is up; `workon` leaves `id:` and
  `p:` out of the time log.

The design's "Broken links" list now says, as its format section
does, that a task with several `p:` goes under its first parent (the
first reading above). Brice accepted, on 2026-11-23, that a 1.0 file
already using `id:N` or `p:N` as ordinary words is read as subtasks
from 1.1; the design's "Compatibility" and GETTING-STARTED say so.

Left open:

- **`htt todo - N`** can't be run: cobra reads `-` as a flag (a known
  1.0 limitation; the e2e test uses `priority N C`).
- **The REPL's hand-over for the question** can't be seen end to end:
  readline 1.5.1 reads nothing between lines on Unix, so reading stdin
  directly passes the pseudo-terminal test too. An in-process test
  pins that the question goes through `runOnTerminal`.
- **Several `id:` on one task**: its first counts, as in topydo; the
  others hold their numbers for new ids, and no warning is given (the
  design lists none).

## Motivation

Build subtasks exactly as [docs/design/subtasks.md](../../design/subtasks.md)
describes them (Brice's design of 2026-11-23, with the TUI's one-level
nest and unnest and priority order among subtasks added the same day).
The design says what subtasks are and how they behave; this plan says
how they're built and tested. Where building shows the design needs to
change, that part stops and is reported, not guessed.

## Choices

### The tree

- **It lives in the domain**, in `internal/domain/tree.go`:
  `NewTree(tasks, doneIDs)` builds it from a context's tasks, purely;
  `Context.Tree()` builds it for a loaded context, reading the done
  file only when some `p:` names no task in the context's own file
  (most loads never read it).
- **A task's id is its first `id:`**, as topydo reads it
  (`tag_value('id')`); links match by exact text, as topydo's do, so
  `p:01` doesn't name `id:1`. A task's parent is named by its first
  `p:` (the design's "each task under its first parent").
- **The context's done file.** htt has one `done.txt` for every
  context; a context's done tasks are those whose `context:`
  annotation names it, as `Context.Complete` writes them. A `p:`
  naming the id of one of those is a done parent.
- **The done file and the archive aren't trees.** They collect tasks
  from every context, so their ids aren't a namespace: htt shows them
  flat, never reorders them and warns about no links in them. Adding,
  nesting and unnesting there are refused; deleting or moving from
  them takes one task.
- **Broken links** are `LinkProblem`s on the tree (a task index and a
  message), each shown at the top level: a `p:` naming no task (nor a
  done one); every task of a loop; a task whose parent's id is on
  several tasks (the warning is on each task holding that id); several
  `p:` on one task, which stays under its first parent (the design's
  format section says so explicitly; its broken-links list puts it
  among the problems that warn).

### Order

- **`Arrange`** puts a context's tasks in tree order: a depth-first
  walk from the top-level tasks, which keep their order; each parent's
  subtasks sorted by priority, `(A)` to `(Z)` then none, stably. It
  only permutes pointers: no line is read back, rebuilt or dropped.
- **On write.** Every persistent `Context` method saves through one
  helper, `Context.save`, which arranges the tasks (and renumbers
  `Line`) before `Repository.Save`. Nothing else writes a context.
- **On read.** `FileRepository.Context` and `MemoryRepository.Context`
  arrange what they read, so a task's number is its place in tree
  order even in a file another tool left out of order, and the tree
  always reads top to bottom in number order. `Line` is the index
  after arranging; `FileLine` stays the line in the file, for
  warnings. A file htt wrote is already in order, so its numbers don't
  change.
- **Priority changes** still sort the context by priority before the
  write, as in 1.0 (the file is sorted after each priority change), so
  top-level tasks sort as they did; `Context.Sort` becomes stable so
  equal priorities keep their order, which the design asks of
  subtasks. The TUI's priority keys stop sorting the reloaded context
  again in memory, which would break the tree's order.

### Ids and arranging

- **Ids:** the smallest whole number whose text no `id:` or `p:` in
  the file uses (every occurrence counts), topydo's `find_next_id`.
- **Adding under N** appends the task with `p:` naming N (N gets an
  `id:` first if it has none); arranging puts it after N's last
  descendant, or at its priority place among N's subtasks.
- **Nesting N under M** moves N's subtree to just after M's subtree,
  then sets N's `p:`, so it lands last among M's subtasks of its
  priority. A task with several `p:` keeps one. A loop is refused, as
  is a parent whose id is on several tasks (a link to it couldn't
  resolve).
- **Unnesting N** (CLI) removes its `p:` tags and moves its subtree to
  just after its top-level ancestor's subtree. A task with no `p:` is
  already top-level: an error.
- **The TUI's one-level moves:** Tab nests the selected task under its
  previous sibling in the tree (its subtree follows it already, so it
  only gets a `p:`); Shift-Tab makes it a sibling of its parent,
  moving its subtree to just after the old parent's subtree, under the
  grandparent or at the top level. `ErrNothingAbove` and
  `ErrTopLevel` say why nothing changed.
- **Moving between contexts** moves the subtree. Into a context file,
  the moved task loses its `p:` (a parent is always in the same file)
  and any of the subtree's ids that clash with an `id:` or `p:` value
  in the target is renumbered to the target's smallest free id, its
  `p:` links rewritten with it. Into the done file or the archive the
  lines go unchanged.
- **Deleting** archives the subtree, in tree order, each line
  annotated as before.
- **Completing** takes a `Subtasks` choice: `SubtasksAsk` (the zero
  value: refuse, with `ErrOpenSubtasks`, when there are open tasks
  below), `SubtasksLeave` (`x`) or `SubtasksComplete` (`A`, every open
  task below at any depth, in tree order). The prompt's count is the
  open tasks below at any depth, which is what `A` completes.

### The completion prompt

- **A terminal** is stdin and stdout both terminals (`isatty`, as the
  REPL checks for the TUI). Without one, and without `--leave-subtasks`
  or `--with-subtasks`, `todo do` fails naming both flags (exit 1).
  Both flags together are an error.
- **Asking:** the four lines of the design on stdout, then one line
  read from stdin a byte at a time (so nothing past it is taken). The
  answer is the line without its `\n` or `\r\n`: exactly `x` or `A`;
  anything else, or end of input, cancels (`Cancelled: nothing
  changed.`, exit 0).
- **In the REPL** the question runs through `runOnTerminal`, the REPL's
  `replTerminal.handOver`, as the TUI does: readline is closed while
  the answer is read, then reopened.

### Showing

- **`htt todo show`** (and `htt todo`, `todo status`, `htt status` and
  the REPL's view) print the tree: two spaces a level after the number;
  a task whose parent is in the done file ends with `(parent done)`.
  `--flat`, `--sort`, `--filter` and `search` print the plain list.
- **Warnings** for broken links go through the date warnings' path
  (`warning: <file>:<line>: <message>` on stderr, once a run), and a
  typed task's command (add, add-to, replace, edit) warns about links
  it broke once it's saved.
- **The TUI** draws the tree with the same indentation, and
  `(N folded)` or `(parent done)` in the muted colour at the end of a
  row; `id:` and `p:` words are muted. Folds are per session, keyed
  by context and id; a search ignores them and shows its rows flat.
  Link warnings join date warnings on the status line.
- **TUI keys** (free in today's keymap and the list's): `s` adds a
  subtask under the selected task, `Tab` nests it under the task
  above, `Shift-Tab` unnests it a level, `Space` folds or unfolds it.
  The selection stays on the task moved; nesting under a folded task
  unfolds it. `x` on a task with open subtasks puts the design's
  question on the status line; the next key answers it (`x`, `A`, any
  other cancels).

## Stages

Each a commit that builds and passes its tests:

1. **The tree and ids** (`tree.go`): building, problems, done parents,
   arranging, id allocation. Pure.
2. **File order on write and read:** `Context.save`, the repositories
   arranging on load, stable `Sort`.
3. **Commands:** the domain operations (add under, nest, unnest, the
   one-level moves, subtree delete and move with renumbering, complete
   with a choice) and the CLI's `--under`, `nest`, `unnest`, `delete`
   and `move` listing what they took, link warnings.
4. **The completion prompt and flags,** CLI and REPL.
5. **`show`:** the tree, `--flat`.
6. **The TUI.**
7. **Docs:** GETTING-STARTED, README, command help, the REPL help,
   TODO.md, docs/architecture.md, the design's status line, this plan
   moved to `complete/` with its outcome.

## Testing

Tests first where they can be, seen failing.

- **Domain, table tests:** each kind of broken link and done parent;
  ids (smallest free, counting `p:`, by text); add under, nest (loop
  refused), unnest, the one-level moves and their "nothing to do"
  cases; move with renumbering (links kept, no clash); delete of a
  subtree; complete with each choice; a priority change moving a
  subtask among its siblings.
- **Domain, property tests** over generated files (lines htt
  rewrites: dates, priorities, done marks; broken links, loops,
  duplicate ids, several `p:`, done-file parents, non-numeric ids):
  arranging is a permutation of the input lines with every line
  unchanged, idempotent, keeps subtrees contiguous under their
  parents, keeps top-level order and sorts siblings by priority
  stably; ids unique and smallest free; moves and renumbering keep
  every line and every link.
- **Through the file repository:** a generated file loads, saves and
  loads again as the same lines; a file in order is written back
  byte-identical.
- **topydo:** a multi-level file as topydo writes it (children before
  and after parents, tags at the end) reads as the tree topydo's rule
  gives; after htt's writes, a test reimplementation of topydo's rule
  reads the same tree back.
- **e2e:** every command; `show`'s indentation and `--flat`, sorted
  and filtered views flat; a command after a reordering write acting
  on the task shown; warnings on stderr once a run; the completion
  prompt through a pseudo-terminal (`x`, `A`, other, end of input),
  in the REPL too; the flags without a terminal, and the refusal.
- **TUI:** the tree unfolded by default; fold and unfold; `s`, Tab
  and Shift-Tab, including their "nothing to do" cases and a task
  with a subtree of its own; the prompt; muted tags; priority keys
  keeping the selection on the task.
- **Mutations** on the core rules, each named with the test that
  caught it; a survivor gets a test.
